# F03: preserve decisions while checking numerical proposal replay

The first clean Linux restoration reached the authenticated language-inquiry parent and rejected an exact dictionary comparison. I reproduced the complete parent computation separately, without admitting or editing its saved evidence. The owner fingerprint was identical. Four uncalibrated alternative proposal scores differed; the maximum absolute difference was 6.548353265883877e-11. All selected frames, alternative orderings, premises, parser identities, simulated intermediate states, cache states and computed results matched exactly. The measured fields are retained in `linux-replay-diagnostic.json`; the local Windows replay has zero differences.

The repair changes only the comparison of `alternatives[*].proposal_score`. Both scores must be finite Python floats in [0,1]. They must satisfy `math.isclose` with relative tolerance `64 * eps(float32)` and absolute tolerance `64 * eps(float32)^2`. Every other interpretation field, including each alternative's ordering and executable frame, still requires exact equality. Derived simulation states, result values, cache identities, checkpoint bytes and original record checksums keep their original exact checks. Scores are neither replaced nor renormalized. This is a bounded replay contract for diagnostic float32-derived scores; it is not a confidence calibration or a change to any scientific evaluation threshold.

Only the audited immediate predecessor graph source, `103f05f6fb895f49d7704022f220feadfca9d8fa5593ee67e79f3e1ef2c5cb15`, receives this compatibility path automatically. Admission is conditional on the exact reviewed successor graph bytes. Other source changes still require the existing explicit migration or rejection. The original graph and compatibility file are retained in `pre-portability-source/`, and the complete original release remains in Git history and its sealed artifacts.

This addresses observed roundoff rather than inferring a general portability guarantee. [PyTorch 2.10's numerical-accuracy documentation](https://docs.pytorch.org/docs/2.10/notes/numerical_accuracy.html) explains why identical floating-point inputs can produce different bits across platforms. Regression tests replay the measured discrepancy, require unchanged input records, reject changed actions/order/sources/premises, reject invalid or excessive score changes and reject unreviewed successor code.
